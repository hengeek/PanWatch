# 代码评审

## 明确评审对象

读取项目 [AGENTS](../../../AGENTS.md)、相关 spec/plan 和差异。明确待评审版本与比较基线；记录实际提交及未提交修改，不臆造基线，不把其他任务的修改归于本次。

不只看 diff：按需要查看调用方、数据流、配置及测试，以确定问题是否可达。范围不足时说明评审限制。

## 评审重点

- 实现是否满足已确认行为与异常反馈，是否改变未授权的范围。
- 错误路径、权限和输入边界、状态一致性、资源生命周期及兼容性是否存在具体缺陷；只检查与本次代码相关的风险。
- 架构边界是否被破坏：`platform` 是否导入 `modules`；模块是否绕过公开 service 直接导入其他模块的 models/repository/router；`packages/*` 是否反向依赖 `src.*` 或数据库；是否恢复已删除的旧目录。
- 数据库变更是否为可重复执行的新迁移，是否修改已发布迁移，是否与模型和测试一致。
- 前端是否符合 [统一 UI 约定](../../../frontend/UI_GUIDELINES.zh-CN.md)：共享组件、亮色/深色、桌面/移动、键盘焦点、中英文 i18n 和市场颜色规则。
- 测试是否能发现关键回归，是否只覆盖成功路径或验证了替代目标；网络、AI、行情和通知是否被正确模拟。
- 数据/配置迁移和产物使用方式是否与实现一致；是否引入真实外部副作用、密钥或隐私数据。
- 改动规模是否超出 [PR 范围预算](../../../docs/pr-policy.zh-CN.md)；若超出，是否可拆成独立可用的改动。

优先报告可由代码或复现证据支持的问题，不为凑数量提出纯个人风格偏好。尚无证据的推测标为待核查，不写成确定缺陷。需要运行检查时使用实际项目命令，记录结果与执行范围：

```bash
make check
.venv/bin/python -m pytest tests/<相关文件> -q
pnpm --dir frontend exec vitest run <相关测试>
```

不触发未经授权的外部操作（真实通知、付费模型、发布、部署）。

## 输出与状态

每条 finding 包含：严重程度（阻断/高/中/低）、文件与位置、触发条件、用户或系统影响、依据及修复方向。路径和行号取自本次实际版本；不虚构复现或失败结果。可选的风格建议与缺陷分开列出。

先列 findings，再说明验证范围、未运行项和遗留风险。未发现问题时写“在本次评审范围内未发现明确缺陷”，不承诺系统无缺陷，不等同于测试、人工接受或发布通过。

用户仅请求评审时不修改源码；用户同时授权修复时，可在范围内修复并分别记录原 finding、修复与重新验证。代码改变后重新核对受影响结论，避免把旧评审套到新版本。

需要持久记录时，写入对应 PR/任务或 [实施日志](../../../docs/templates/implementation-log.md) 的评审条目，不创建第二份 spec 或架构事实源。
