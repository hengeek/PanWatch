# 技术方案设计

## 输入与定位

读取项目 [AGENTS](../../../AGENTS.md)、[README](../../../README.md)、相关 spec、[当前架构](../../../docs/arch/arch.md)、[后端架构](../../../src/ARCHITECTURE.md) 与实际代码/配置。需求决定接受条件，当前代码决定实现事实；历史设计提案不能当成已实施架构。

确认需求中的阻塞缺口。非阻塞信息可采用标明的假设，不自行替用户决定产品行为。

## 方案形成

- 定位实际入口、受影响模块与现有复用能力，说明当前行为与目标行为的差异。
- 优先选择满足需求的最小可维护方案。只有存在有意义的取舍时才比较备选；不要给简单任务强加微服务、分层或额外依赖。
- 明确模块职责、依赖方向、接口契约、错误处理，以及适用的数据一致性、权限和外部服务边界。遵守以下 PanWatch 约束：
  - `web → modules → platform`；模块之间通过公开 service、DTO 或 event 协作。
  - `packages/*` 不得反向导入 `src.*`、FastAPI、SQLAlchemy 或数据库。
  - 新 AI/行情/通知供应商放入对应 `platform/*` adapter；新业务工作流放入 `modules/<domain>`。
  - 数据库 schema 变更只追加可重复执行的新版本迁移，不修改已发布迁移。
  - 前端先读 [统一 UI 约定](../../../frontend/UI_GUIDELINES.zh-CN.md)，复用共享组件；用户可见文案同步中英文 i18n。
- 有已有数据、调用方或运行系统时，说明兼容方式、迁移顺序、失败恢复与回退；没有相关影响则直接写明。
- 把实施步骤关联到需求验收条件，列出需要修改的范围、依赖、验证方法和产物；工具链与命令从 `foundry.json`、`Makefile` 和 CI 取得，未配置时标为未配置。
- 仅在多任务协作有实际收益且已获授权时规划任务拆分，明确公共文件所有者与集成顺序；本技能本身不要求启动子 Agent。

## 结果落点

采用 [实施计划样板](../../../docs/templates/implementation-plan.md)，写入或完善 `docs/impls/` 的对应方案，更新 [实施索引](../../../docs/impls/README.md)。小修复可在原任务内说明方案；大型任务按开发规范增加摘要与必要的 brief。

方案应包含当前事实、拟采用的结构、主要取舍、文件/接口影响、实施顺序、验证与遗留决策。只请求设计时不直接实现代码。

待实施方案保留在 plan；确认且已经实施的长期架构事实再同步到 [当前架构](../../../docs/arch/arch.md) 或 [后端架构](../../../src/ARCHITECTURE.md)，不把拟议方案写成系统现状。交付时分别说明已确认、建议和待解决项。
