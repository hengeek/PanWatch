# 需求分析

## 输入与定位

先读取项目 [AGENTS](../../../AGENTS.md)、[README](../../../README.md)、[产品目标](../../../docs/product/vision.md)、相关现有需求和用户提供的资料。范围与证据要求参考 [PR 规范](../../../docs/pr-policy.zh-CN.md)，环境与提交流程参考 [贡献指南](../../../CONTRIBUTING.zh-CN.md)。

区分已确认事实、假设与待确认问题；没有资料时不编造用户、业务规则、行情供应商或外部依赖。

本技能同时分析产品目标与可测性，不局限于 QA 缺口清单。技术实现选择留给实施方案，除非它已经是用户约束。

## 分析方法

- 明确谁在什么场景遇到什么问题、期望结果，以及本次范围和明确暂缓事项。
- 描述关键操作、输入、状态变化、输出和失败反馈。按 PanWatch 的实际领域检查：
  - 市场与标的：A 股、港股、美股、ETF；代码规范化、币种、交易日历和时区。
  - 组合与纸面交易：账户、持仓、盈亏、费用模型和并发操作。
  - AI 与研究：模型供应商、凭证、费用、失败回退、证据和结果可追溯性。
  - 提醒与通知：条件组合、冷却、每日限额、过期、交易日限制和真实送达。
  - 助手与 Agent：工具权限、审批、暂停/恢复、资源限制和运行记录。
  - 前端与 PWA：中英文文案、亮色/深色、桌面/移动、键盘与可访问性。
- 将关键行为写成可观察的验收条件，必要时编号 `AC-01`；包含正常、重要异常与边界。避免“运行正常”“性能良好”等无法验证的表达。
- 区分“什么行为被接受”和“用什么测试证明”。自动测试、人工操作或外部真实调用按实际能力安排。
- 仅对会改变范围、授权、数据或接受标准的缺口提出关键问题。能独立分析的内容继续完成；有缺口的初稿保持 `draft`，不把假设标为已批准。
- 需求规模明显超出 [PR 范围预算](../../../docs/pr-policy.zh-CN.md) 时，先讨论可独立交付的最小版本，不把一个不可用的功能拆成多个必需 PR。

## 结果落点

按 [需求样板](../../../docs/templates/feature-spec.md) 完善 `docs/features/` 下的真实需求，更新 [需求索引](../../../docs/features/README.md)。用户只请求分析或评审时，先在回复中给结果，不自行将其登记为已接受。

编号使用真实 Issue 或项目内唯一编号（如 `FEAT-001`）。已有 spec 优先修订同一事实源，保留重要范围变更；不要为了使用技能再创建重复文档。小修复可在已有任务记录或 PR 内写清行为与验证。

交付时概括目标与范围、关键行为、验收条件、重要缺口及下一步。需求尚未确认的部分明确标识，不直接扩展实现范围。
