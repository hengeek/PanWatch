# 问题定位

## 固定问题上下文

读取项目 [AGENTS](../../../AGENTS.md)、相关需求、代码和已有执行记录。记录预期与实际行为、环境、版本、最小输入、错误信息、近期变化和复现频率。保护现场与用户未提交内容，不将恢复或清理当成默认步骤。

PanWatch 常见定位入口：

- 后端日志、数据库日志处理器和 SSE 事件；运行状态与设置页面。
- `make doctor`：数据源、AI、通知、DB、磁盘和调度自检。
- `.venv/bin/python -m pytest tests/<相关文件> -q` 与 `frontend` 的 Vitest 用例。
- 需要真实服务或隔离环境时，使用 [panwatch-local-delivery](../panwatch-local-delivery/SKILL.md) 的隔离准备与验收流程。

缺少环境或访问条件时，先分析可获得的代码和日志，提出最小必要补充信息；不要把“无法复现”写成“问题不存在”。日志与测试数据使用脱敏内容。

## 从复现到原因

- 尽可能建立最小复现，并确认错误来自目标版本与环境；间歇故障记录发生条件和频率。
- 沿输入、调用链、状态与外部边界定位最早偏离预期的位置，区分表面症状、相关现象与原因。重点关注：模块边界处的契约、数据库迁移与模型不一致、时区/交易日历、供应商失败回退、Agent 工具审批、前端状态与 i18n。
- 为重要假设说明依据、可以区分假设的检查与实际观察；优先小范围验证，避免同时改动多处而无法判断因果。
- 若验证涉及真实数据修改、清理、重启、通知发送或付费模型调用，先判断是否已在用户授权内；未授权则使用只读证据或隔离复现，不靠技能扩大权限。
- 有新证据时修正假设；重复尝试没有新增信息时，汇总已排除项和具体阻塞，不以大范围重构代替诊断。

## 修复与验证

只请求定位时交付原因与建议；已授权修复时，针对原因做最小有效修改，不用吞错、跳过断言或删除用例制造通过。

先重跑原复现，再检查相关路径和回归。适合自动化且能保护真实行为时补回归测试；不要为文案或低风险可逆改动强制增加测试。涉及模块边界、迁移或前端交互时，运行对应的架构测试、后端测试、前端测试与 `make check`。环境无法运行时区分代码推断与实际验证。

## 结果落点

在对应任务或 [实施日志](../../../docs/templates/implementation-log.md) 中记录：复现、证据、验证过的假设、原因可信度、修改、回归结果与剩余限制。区分“原因已证实”“原因待验证”“修复已验证”和“尚未验证”。

长期有效的系统事实同步到 [当前架构](../../../docs/arch/arch.md) 或 [后端架构](../../../src/ARCHITECTURE.md)；不将每次故障历史复制进架构文件。交付说明原问题是否消失、依据及尚未覆盖的条件。
