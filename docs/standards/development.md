# PanWatch 开发规范

规范版本：1.0.0（PanWatch 落地版）  
框架来源：code-foundry 0.1.1 / 通用规范 1.0.0  
落地日期：2026-11-11

本文是 PanWatch 的项目级开发规范，说明必须满足的工程约束。环境安装、提交信息和 PR 模板以 [贡献指南](../../CONTRIBUTING.zh-CN.md) 为准；PR 范围、证据和自动关闭规则以 [PR 规范](../pr-policy.zh-CN.md) 为准。本文不重复这两份文档的细节。

## 1. 规则级别与项目元信息

- **必须**：项目应落实；暂未落实时记录原因、影响、负责人及完成条件。
- **建议**：有实际收益时采用，简化时说明替代办法。
- **可选**：按实际能力启用，不创建假成功脚本或无用途的空实现。

项目名、负责人、技术栈、目标平台、默认分支、许可证、外部依赖和模板版本记录在根 `foundry.json`。当前技术栈和命令已经确定；`null` 表示尚未配置，不代表默认通过。

业务开发前先明确产品目标、关键边界和验收标准。密钥、私人持仓、本地数据库、生成报告和缓存不进入版本库。依赖清单与锁文件（`requirements*.txt`、`frontend/pnpm-lock.yaml`）必须同步提交。

## 2. 目录与文件职责

| 位置 | 职责 |
|---|---|
| 根 `README.md` | 产品介绍、功能、快速开始与参考链接 |
| 根 `AGENTS.md` | AI 阅读入口、项目地图、真实命令与执行边界 |
| 根 `CONTRIBUTING*.md` | 环境、开发流程、测试、提交信息与 PR 要求 |
| `foundry.json` | 项目元信息、技术栈、真实命令与文档入口 |
| `server.py` | 后端进程入口：FastAPI、数据库、调度器和通知装配 |
| `src/bootstrap/` | 唯一创建 FastAPI 应用和注册 router 的位置 |
| `src/modules/` | 产品业务能力，每个一级目录拥有一个能力 |
| `src/platform/` | AI、持久化、行情、事件、调度、通知、可观测、运行时 |
| `src/web/` | 跨模块复用的 HTTP 中间件与响应适配 |
| `packages/` | 可独立复用的 Python 包；不得反向导入 PanWatch 应用或数据库 |
| `frontend/src/` | React 页面、组件、Hook、路由与多语言资源 |
| `frontend/packages/` | 前端共享 API、基础 UI 与业务 UI |
| `prompts/` | 分析流程 Prompt 模板 |
| `tests/` | 后端、集成、架构边界和评测测试 |
| `frontend/tests/` | Vitest 与 Testing Library 测试 |
| `scripts/` | 构建、预发布检查、隔离 QA、评测等工程脚本 |
| `.agents/skills/` | 随仓库分发的项目技能 |
| `docs/` | 产品、架构、规范、需求、实施、验收与素材 |
| `docs/features/`、`docs/impls/` | 活跃需求与实施记录；归档进入各自 `archive/` |

后端模块与依赖方向以 [后端架构](../../src/ARCHITECTURE.md) 为唯一详细事实源。不得恢复已删除的 `src/collectors/`、`src/models/`、`src/compat/`、`src/web/api/`、`src/web/app.py`、`src/web/database.py`、`src/web/models.py` 或 `src/web/migrations.py`。

## 3. 单一 Agent 指南

`AGENTS.md` 保持简短，提供阅读顺序、项目地图、真实命令、模块约束、验证要求和外部操作边界。详细需求、方案和历史放在所属文档，不复制到所有入口。

`CLAUDE.md` 只引用 `AGENTS.md`，不维护第二套规则；它已被 `.gitignore` 忽略，是本地入口。新增其他工具入口也遵循同一原则。协调、实现、评审职责与具体模型选择分开描述，不因使用某一工具而省略需求和验证记录。

公共开发方法见 [技能索引](../skills.md)。按任务选择需求分析、技术方案、代码评审、问题定位或交付验证；技能执行结果复用既有文档，不替代验收或扩大授权。仓库技能保留在 `.agents/skills/` 和 `docs/` 的相对位置。

## 4. 统一任务契约

| 任务 | 当前命令 | 必须满足的行为 |
|---|---|---|
| help | `make help` | 未安装业务依赖时也能查看命令与前置条件 |
| setup | `make setup-backend`；`pnpm --dir frontend install --frozen-lockfile` | 按清单准备依赖，不隐式升级、不覆盖本地配置 |
| run | `make dev-api`；`make dev-web` | 启动真实后端/前端，正确处理端口、错误与中断 |
| check | `make check` | 后端编译检查、前端 UI/i18n/市场色检查、空白符检查；不修改源码 |
| fmt | 未配置 | 不提供假格式化命令；提交前至少运行 `git diff --check`，前端构建包含 `tsc -b` |
| test | `make test`；`pnpm --dir frontend exec vitest run` | 执行真实测试；断言失败非零退出，意外零用例失败 |
| verify | `make verify` | 聚合 check、后端测试、前端测试和 `packages/*/tests` |
| build | `make build VERSION=<version>` | 构建前端与 Docker 镜像，并验证产物 |
| eval | `make eval` | 运行 Agent 过程评测；chat 用例需要 `EVAL_AI_*` |
| doctor | `make doctor` | 检查数据源、AI、通知、DB、磁盘和调度 |

脚本基于项目根目录运行，处理中文和空格路径、参数、退出码及中断。禁止以无条件成功、吞掉异常或跳过断言等方式掩盖失败。构建不隐含提交、消息发送、部署或发布。

前端检查的最小集合与 [统一 UI 约定](../../frontend/UI_GUIDELINES.zh-CN.md) 一致：`pnpm check:ui`、`pnpm check:i18n`、`pnpm check:market-colors`、相关 Vitest 测试和 `pnpm build`。

## 5. 依赖、工具链与 CI

- Python 3.10 或更高版本；Docker 运行时使用 Python 3.11。
- Node.js 24.14.0；pnpm 9.15.9。
- 后端依赖按 `requirements*.txt` 安装；前端按 `frontend/pnpm-lock.yaml` 安装。
- 锁文件与清单同步变更；主动升级依赖与按锁安装分开执行。

现有 GitHub Actions 工作流：

| 工作流 | 职责 |
|---|---|
| `ci.yml` | 前端检查、前端测试与构建；后端测试与 `packages/*/tests` |
| `frontend-i18n.yml` | 前端国际化文案与 key 检查 |
| `javascript-runtime.yml` | JavaScript 运行时相关检查 |
| `timezones.yml` | 时区规则检查 |
| `pr-policy*.yml` | PR 范围、报告结构和自动关闭策略 |
| `release.yml`、`docker-image.yml` | 发布与镜像构建 |

CI、本地执行、独立评审、人工接受、已合并、已发布分别记录。仅编译成功不能证明目标平台可运行；本机通过不能登记为远程 CI 或其他平台通过。分支保护与必需检查需在托管平台实际配置，不因有 YAML 文件而自动存在。

## 6. 按任务规模组织文档

| 类型 | 建议产物 |
|---|---|
| 小修复 | 任务说明、变更范围与验证记录，可写在 Issue/PR |
| 普通功能 | `docs/features/<编号>-<主题>.md` 与 `docs/impls/<编号>-<主题>.md` |
| 大型需求 | spec 与 `docs/impls/<编号>-<主题>/` 任务目录 |
| UI 变化 | 在对应文档中补设计引用、交互规则和验收记录 |

大型任务目录包含 README 状态摘要、`plan.md`、`impl_log.md`，按需增加 `briefs/` 与 `trace.md`。普通功能可在一份实施文档中合并计划、执行日志和交接上下文，避免为了套格式重复记录。

spec 维护用户行为与接受条件，plan 维护实现方案，日志记录执行事实，架构说明维护当前系统。一个事实选择一处维护，其他文档通过链接关联。

样板见 [文档样板索引](../templates/README.md)。模板中的方括号提示允许保留，真实任务文档中影响执行的信息必须在开发前填写。

## 7. 可交接任务与协作

一个任务应有明确目标、修改范围、交付物与验收标准。完整 brief 至少覆盖：任务编号、关联需求、当前事实、最小阅读上下文、基线提交、分支/worktree、依赖接受状态、文件归属、接口约束、验证命令、外部条件、交付格式和阻塞升级方式。

普通功能可以在实施计划中合并这些字段；大型任务为独立执行单元建立 [brief](../templates/phase-brief.md)。没有历史聊天上下文的人也应能据此开始。

普通需求按“计划 → 实现与评审 → 验收与合并”推进；大型需求先拆阶段，再拆边界明确的任务。评审指出问题位置、影响与复现方式，实现者修复后重跑相关验证。重复失败按项目约定升级，不降低标准。

若采用多 Agent 或多 worktree：

- 协调者维护依赖、公共契约、任务状态和集成顺序。
- 可并行任务必须边界独立；共享 schema、路由入口等公共文件明确单一所有者或顺序依赖。
- 各任务明确已提交基线。配置、端口、可写数据库和输出目录按任务隔离，不能只依赖 worktree 隔离。
- 工作者回报事实与证据，协调者统一更新共享日志与状态，避免互相覆盖。
- 独立任务通过后仍需验证最终集成结果；工具显示任务结束不等于验收完成。
- 清理前确认未提交、未合并内容及归属，保留必要证据。

本地隔离实服验收、证据报告和 PR 附件交付使用 [panwatch-local-delivery](../../.agents/skills/panwatch-local-delivery/SKILL.md)；它不替代 spec、plan、commit 和验收记录。

## 8. 需求到交付的追溯

采用真实 Issue 编号；无 Issue 系统时使用项目唯一编号（如 `FEAT-001`）。不捏造外部链接。

追溯链为：任务 → spec 的需求与验收条件 → plan/brief → commit/PR → 实际检查与验收证据 → 合并、发布或归档记录。

重要验收条件编号为 `AC-01` 等。验证记录说明对应条件、提交或文件版本、环境、命令、结果及证据。使用 `PASS` / `FAIL` / `未执行`，失败不能改记未执行；真实调用、模拟和未验证分别记录。

普通功能在 spec 或 PR 维护追溯表；大型任务按需建立 `trace.md`，其他位置引用它。PR 说明需求、实现范围、测试版本与结果、兼容性和遗留项。索引至少包含名称、状态、文档链接和任务引用。

## 9. 验收与完成标准

完成应具备真实实现、适用检查、评审、人工接受及遗留说明。示例 smoke 通过不能代表新业务的权限、UI、性能或外部集成均已验收。

执行记录保留失败与修复过程。无法执行的验证写明原因、影响、负责人和补齐条件。源码变更后重新评估旧证据是否仍有效。合并、发布和对外动作按用户授权执行。

真实 AI 模型、行情供应商、通知送达和外部账号操作分别记录。模拟发送、HTTP 200、进程存活或数据库存在不能单独证明业务验收通过。

## 10. 归档规则

已按接受标准交付、被替代或明确取消时归档；仅代码写完、评审通过或仍待验收时，不能按已交付归档。

归档前：

1. 确认最终状态、接受人、PR/commit 和实际发布状态。
2. 将有效决策、产品规则与运行方式更新到当前架构或长期说明。
3. 为遗留项建立可追溯任务，明确负责人、影响和完成条件。
4. 保存必要的脱敏证据及访问、保留条件。
5. 文档保留原名迁入对应 `archive/`，大型任务整体迁移。
6. 更新文档链接、活跃与归档索引；必要时保留旧链接的短跳转页。

归档元信息包括日期、最终状态、任务和提交、原因、替代文档、遗留项。取消记录保留取消原因。当前架构、当前产品规则与仍适用的 smoke 清单持续维护，不随实施任务归档而移走。

重新启用归档任务时建立新任务或明确恢复记录，并重新检查旧结论。参见 [追溯与归档样板](../templates/trace-and-archive.md)。

## 11. 框架维护

采用版本和项目调整记录在 `foundry.json` 与对应文档中。当前没有自动升级工具；吸收 code-foundry 模板变化时人工比较，保留项目已有决定与业务文件。

新增技术栈、脚本、依赖或 CI 后执行受影响的实际检查，更新命令、索引和验证范围。定期检查失效链接、重复文档、长期停滞任务及过期规则。

## 12. 当前执行边界

本次改造已建立项目级规范、Agent 入口、需求/实施/验收文档骨架和六个项目技能。验证记录见 [框架落地验证](../verification.md)。在依赖安装、真实服务和外部供应商未执行的部分，不登记为通过。
